Virtual memory, measured

The Address Is Not The Memory

A process on this machine can address 128 TiB. The machine has 15 GB of RAM. Neither number is a mistake, and the gap between them is not a rounding error — it is the whole abstraction. Every address your program handles is a lookup key, not a location, and almost none of the keys resolve to anything at all.

AMD Ryzen AI 9 HX 370 · Linux · gcc 13.3 48-bit addresses · 47 bits for userspace 4 KB pages, 2 MB huge pages 15.3 GB RAM · 15.3 GB swap

01What a process actually has

The textbook picture of a process's memory is four stacked boxes — code, data, heap, stack — and a note that shared libraries go somewhere. That picture is not wrong so much as it is the wrong scale. Here is what address_space.c finds when it reads its own /proc/self/maps:

virtual size66.6 MBwhat it can address
resident2.7 MBwhat it costs in DRAM
resident / virtual4.1 %the rest is a promise
user address space131,072 GB247 bytes
fraction of it mapped0.000050 %—

02How an address becomes a location

If the address is a key, something has to look it up. On x86-64 that something is a four-level tree walked by the hardware on every access that is not already cached. The address is not one number to the MMU — it is five fields.

The tables are made of memory too

Nine bits per level means 512 entries of 8 bytes — one 4 KB page per table. Those pages are real. Touching 1 GB of anonymous memory on this machine grows the process's page tables from 44 KB to 2,100 KB: exactly 8 bytes of table per 4 KB page mapped, an 0.2% tax that appears only as you touch. A 64 GB reservation that is never touched costs 44 KB, because the tree is built lazily too.

03Allocation is a promise, not memory

A successful malloc buys addresses. Physical pages arrive later, one at a time, when each is first touched. On a machine with 15 GB of RAM, lazy_alloc.c asks for 64 GB and gets it: 

VmSize       2.6 MB ->  65538.6 MB   (+65536 MB)   addresses: granted immediately
VmRSS        1.7 MB ->      1.8 MB   (+0.1 MB)    memory: nothing arrived

The kernel will not promise absolutely anything

With MAP_NORESERVE this machine reserved 512 GB without complaint — address space costs nothing to hand out. Without it, the default heuristic (vm.overcommit_memory = 0) accepted 16 GB and refused 32 GB. That ceiling is RAM plus swap, 15.3 + 15.3 ≈ 30 GB: the kernel declines commitments it could not conceivably honour, but is perfectly willing to make ones it merely probably cannot.

04What the promise costs to keep

Every page of a fresh mapping costs one trap into the kernel the first time it is touched: find a free frame, zero it (the previous tenant's data cannot leak), install a page-table entry, return. fault_cost.c times that, and checks every case against the kernel's own fault counters from getrusage rather than trusting the clock alone.

  1. 1

    Huge pages make faults rarer, not cheaper

    256 MB costs 65,539 faults with 4 KB pages and 128 with 2 MB pages — exactly one per huge page. Each is more expensive individually (the kernel zeroes 2 MB, not 4 KB), but per byte it wins: 853 ns → 277 ns.

  2. 2

    MAP_POPULATE moves the cost, it does not remove it

    The faults are taken inside the mmap call — 627 ns per page there, and then the touch loop runs at warm speed. Useful when you would rather pay at startup than in the middle of a request, useless as an optimization.

  3. 3

    Readahead does for pages what a prefetcher does for lines

    Reading a 256 MB cold file sequentially should mean 65,536 trips to the SSD. It cost 2,052 faults and one blocking read: the kernel saw the pattern and fetched ahead. Touch the same file in random order and that collapses — 703 real major faults.

05fork copies an address space without copying memory

fork is specified to give the child a complete private copy of the parent's memory. Doing that literally would mean copying every resident page. The kernel instead marks every writable page read-only in both processes and lets them share the frames until someone writes. The write traps, one page is copied, both continue.

06The same address is not the same memory

"The addresses don't correspond to hardware addresses" is easy to nod at. So force the issue: two processes, the same 64-bit number — not similar, not analogous, the identical address — and ask each what it finds there. 

both processes map the very same virtual address: 0x600000000000

private + anonymous  →  each process gets its own frame
  A writes  "written by process A"  at 0x600000000000
  B reads   "written by process B"  at 0x600000000000

shared + file-backed  →  both processes get the same frame
  A writes  "written by process A"  at 0x600000000000
  B reads   "written by process A"  at 0x600000000000

Same number, opposite outcomes. The only thing that changed is one flag on the mmap call, which decides whether the two page-table entries point at one physical frame or two. The address is not the memory; the entry behind it is. Isolation between processes is not enforced by checking addresses — it is a consequence of never writing the same frame into two tables.

07What the abstraction buys, and what it costs

Virtual memory is usually introduced as one idea — programs get their own address space — when it is really a set of separate services that happen to share a mechanism. Each row below is something the page table makes possible, and the price this machine charges for it.

the promise

Each process has memory to itself.

the mechanism, and its price

Separate page tables. Free at runtime; costs a TLB flush at every context switch, and 8 bytes of table per mapped page.

the promise

You may allocate more than exists.

the mechanism, and its price

Reservations with no frames behind them. Free until touched; the bill arrives as 853 ns per page, or as the OOM killer if the promise cannot be met.

the promise

fork duplicates your memory.

the mechanism, and its price

Copy-on-write sharing. 2.3 ms for 256 MB; then 1,308 ns for each page the child actually writes.

the promise

Processes can share memory deliberately.

the mechanism, and its price

Two entries, one frame. Free — and the reason one copy of libc serves every process on the machine.

the promise

Memory can outlive RAM.

the mechanism, and its price

Pages backed by a file or by swap. 55.2 µs per major fault on this NVMe — roughly 70,000 instructions of waiting.

the promise

Code cannot be written; data cannot be run.

the mechanism, and its price

Permission bits in the entry, checked by hardware. Free, and the reason this process has 1.7 MB mapped executable and 64.4 MB mapped writable with no overlap.

The one number to carry away

4.1%. That is how much of this process's mapped address space had physical memory behind it — and its address space is itself 0.00005% of what it could address. Virtual memory is not mostly about translation; it is about how much you can convincingly not do.

How this was measured

Five small C programs, no privileges required, reading /proc/self/maps, /proc/self/status, /proc/self/smaps_rollup and /proc/self/pagemap, with fault counts from getrusage. Physical frame numbers in pagemap are zeroed for unprivileged readers, which is why §06 demonstrates frame identity by what each process can see rather than by printing frame numbers.

The cold-file cases evict their own pages with posix_fadvise(POSIX_FADV_DONTNEED) rather than dropping the system's caches, and the scratch file lives on the NVMe rather than tmpfs — otherwise "cold" would be served from RAM and measure nothing.
