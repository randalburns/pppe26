An introduction

Three Illusions

Three things your program believes that are not true: that it has the machine's memory to itself, that malloc gave it memory, and that fork copied that memory. Each belief is useful, each is maintained by a specific mechanism, and knowing the mechanism explains a surprising amount of behaviour that otherwise looks arbitrary.

Chapter one

Virtual memory

Start with the problem, not the solution. Suppose there were no virtual memory: every program names memory by its real, physical location.

Three difficulties appear immediately. First, two programs cannot both use location 1000, so every program must be built knowing what else will be running — an impossible requirement. Second, nothing stops a program from writing to another program's data; a single stray pointer takes down the machine. Third, a program needs its memory in one contiguous run, so it cannot start unless a large enough gap happens to be free, even when plenty of total memory is available.

All three problems are about names. And the standard fix for a naming problem is a layer of indirection.

The idea

Give every process its own private set of names, and keep a table that translates those names into real locations. The names are virtual addresses; the real locations are physical addresses; the table is the page table. Because each process has its own table, process A's address 1000 and process B's address 1000 can lead wherever the operating system chooses — including to two entirely different places.

Translating every individual byte would need a table larger than the memory it describes. So memory is translated in fixed-size blocks called pages — 4096 bytes on most machines, including the one behind this page. A virtual address splits in two: the upper bits name a page, and the lower 12 bits are an offset within it. Only the page number gets translated; the offset is carried across untouched.

A worked translation

Suppose a program reads virtual address 0x1234 and pages are 4096 bytes (0x1000). Split the address: 

0x1234  =  0x1 234
               └── page number 1
                  └── offset 0x234 = 564 bytes into the page

look up page 1 in this process's page table  →  frame 17
physical address  =  frame 17 × 4096 + 564  =  0x11234

Notice that the last three hex digits did not change. Within a page, virtual and physical addresses differ by a constant, which is exactly why the page is the unit of everything that follows.

A common confusion

The page table is not consulted by your program, your compiler, or even the operating system on each access — it is walked by hardware, on every load and store, invisibly. The operating system's job is only to build and maintain the tables. This is why virtual memory costs so little in the common case and why it cannot be turned off for a program that would rather go fast.

What the indirection buys

  • Isolation. A process cannot name what is not in its table. This is the entire mechanism; there is no additional guard.
  • Sharing, when wanted. Two entries can point at one frame — libraries, shared buffers, memory-mapped files.
  • Contiguity, faked. A program's memory looks like one unbroken run to the program, while the frames behind it are scattered wherever there was room.
  • Protection. Each entry carries permission bits, so a page can be readable but not writable, or writable but not executable. The hardware enforces it.
  • More memory than exists. An entry can say "not present", and the operating system can fetch the page from disk when it is touched. This is the part that makes the next chapter possible.
In a nutshell

An address is a name, not a place. The page table turns names into places, one 4096-byte page at a time, and every useful property of a modern process — isolation, sharing, protection, memory that is not there — falls out of controlling that table.

Check yourself

Two processes each print the address of a variable, and both print 0x7ffd4a2b18. Are they using the same memory?

Almost certainly not. They are using the same name. Unless the two processes deliberately arranged to share (with mmap and a shared file or a shared-memory object), their page tables send that identical address to different frames. The companion page demonstrates exactly this experiment on real hardware.

Chapter two

malloc

It is worth being blunt about what malloc is not. It is not a system call. It is not part of the operating system. And it does not, in the moment you call it, give you any memory.

malloc is an ordinary function in an ordinary library, written in C, running in your process like any other code you call. Its job is to be a retailer: it buys memory from the operating system in large amounts, infrequently, and hands it back to you in whatever odd little sizes you ask for.

Why a middleman is needed at all

The operating system deals only in whole pages, and asking it for memory means a system call — a trap into the kernel, hundreds of times more expensive than a function call. A program that asked the kernel directly for each of its ten million 24-byte structures would spend all of its time in the kernel and waste 4072 bytes out of every 4096.

So malloc keeps a pool. When you ask for 24 bytes it carves them from a chunk it already owns, and returns in a few dozen nanoseconds without the kernel being involved at all. Only when the pool runs low does it go to the kernel — for a megabyte or more at a time.

Two calls, two very different stories

callwhat usually happens
malloc(24) malloc finds a free chunk in its pool, marks it used, returns a pointer. No system call, no kernel, tens of nanoseconds. The memory has existed since the last time the pool grew.
malloc(10 MB) Too big to carve out, so malloc asks the kernel directly with mmap. The kernel notes a new region in the page table and returns — without allocating any physical memory. The pages arrive one at a time, as you write to them.
A common confusion

free() usually does not return memory to the operating system. It returns the chunk to malloc's pool, where it waits to satisfy your next request. This is why a program's memory use, as reported by the system, so often goes up and stays up even though the program frees everything it allocates. It is not a leak — it is a retailer keeping stock on the shelf.

In a nutshell

malloc is a library that resells memory. It gives you an address immediately, involves the kernel rarely, and the physical memory shows up later still — on the first write to each page. Three separate events, easily mistaken for one.

Check yourself

A program calls malloc(1 GB) on a machine with 8 GB of RAM, and it succeeds. Then it calls it four more times, and those succeed too. Is the machine about to run out of memory?

Not yet, and possibly never. Five gigabytes of addresses have been handed out; no physical memory has been committed. If the program writes to only the first few megabytes of each region, that is all it will ever consume. Trouble comes at touch time, not allocation time — and if the machine cannot then keep the promise, the failure arrives as a killed process rather than as a null pointer from malloc.

Chapter three

fork

fork is the only way to create a process on a Unix system, and it works in a way that surprises nearly everyone the first time: it does not start a new program. It makes a duplicate of the one already running.

After fork returns, there are two processes. Both have the same code, the same variables with the same values, the same open files, and both are sitting at the same instruction — the one just after the fork. The only thing that differs is the value fork returned. 

pid_t pid = fork();

if (pid == 0) {
    /* only the child gets here: fork returned 0 */
    printf("I am the child\n");
} else {
    /* only the parent gets here: fork returned the child's pid */
    printf("I am the parent of %d\n", pid);
}

One call, two returns. That single asymmetry — zero to the child, the child's process id to the parent — is the whole mechanism by which the two copies tell themselves apart.

Why the copy is usually wasted, and why that is fine

The overwhelmingly common use of fork is to follow it immediately with exec, which throws the whole address space away and loads a different program. That is what a shell does every time you run a command. Copying the parent's memory in order to discard it a microsecond later would be pure waste — and with copy-on-write, almost none of it ever happens.

A common confusion

A program prints one line, then forks, and the line appears twice. Nothing printed it twice. Output is buffered inside the process, and if the buffer had not yet been flushed when fork ran, the child inherited a copy of it — and both processes flushed it on exit. Flush before forking, and the problem disappears. This is not a hypothetical; it happened while writing the companion page, and cost the child's entire output.

In a nutshell

fork duplicates a process by duplicating its page table and sharing every frame read-only. The copy is real but lazy: it happens one page at a time, only for pages that are actually written, and often never happens at all.

Check yourself

A parent process holds a 4 GB in-memory index and forks 8 worker children that only read it. Does the machine now need 36 GB?

No — it needs a little over 4 GB. All nine processes share one set of frames, and readers never trigger a copy. This is exactly why the pre-fork server model works. It also explains the failure mode: if the children start writing to that index, memory use climbs steadily as pages diverge, and a machine that was comfortable can run out with no change in the number of processes.

Putting it together

One mechanism, three illusions

All three chapters describe the same table doing the same job. Virtual memory is what the page table is; malloc and fork are two things you can do with it.

the illusionwhat really happens
My program has memory to itself It has a private page table. Isolation is the absence of entries, not the presence of checks.
malloc gave me 10 MB It gave you 10 MB of addresses. Frames are attached one page at a time, on first write.
fork copied my memory It copied your page table and marked the frames read-only. Pages copy themselves, later, only if written.

Each illusion is worth maintaining, and each becomes a source of confusion the moment you need to reason about performance or about how much memory a program really uses. The pattern to carry forward is that in all three cases the expensive part is deferred to the first write — which is why the memory a program consumes correlates with what it touches, not with what it asks for.
