Vectorized Quicksort

Quicksort spends nearly all its time in one loop: partitioning. Replacing that loop's scattered in-place swaps with two sequential streams is what makes a SIMD version worth building.

Bramas, arXiv:1704.08579 · measured on AMD Ryzen AI 9 HX 370 (Zen 5), Highway 1.0.7, GCC 13.3

Classic quicksort partitions with Hoare's two-pointer scan: walk in from both ends, and whenever a pair is out of place, swap it. The comparisons are cheap, but the writes land wherever the pointers happen to be — scattered across the whole subarray.

The vectorized version keeps the same recursion and the same median-of-3 pivot. It changes only the partition, using a SIMD instruction called CompressStore that packs the selected lanes of a register into contiguous memory. That single substitution turns the write pattern from random to sequential.

Everything below is measured on Zen 5. The partition is portable Highway; the 16-element base case is a hand-written 2×256-bit AVX2 network. At the AVX2 target the vector is 8 lanes of int32; under AVX-512 it is 16.

01The primitive: CompressStore

Load a block of lanes, compare all of them against a broadcast pivot in one instruction, then write each group out packed together. CompressStore skips the lanes the mask rejects and closes the gaps — the survivors land contiguously.

02One partition pass

The whole subarray streams through that block loop. Two counters, lc and rc, track how far each scratch buffer has filled. A short scalar loop mops up the elements that do not fill a whole vector, then both buffers are copied back over the original range.

03Why it wins: the write pattern

Both partitions read every element once. The difference is entirely in where they write. Hoare writes in place, at two pointers that wander toward each other; CompressStore writes forward into two buffers and never revisits an address.

04Where the recursion stops

Partitioning is only worth it while the subarray is large. Below 16 elements the vector loop cannot fill even one register, so the recursion hands off to a branchless sorting network — or, smaller still, to plain insertion sort.

Two things the port turned up

AVX-512 is slower than AVX2 here. Zen 5 has vpcompressd, the single instruction the paper was written around, and Highway selects it at -march=native with 16 lanes instead of 8. It loses:

Both compilers agree, at about 7%. Wider vectors mean fewer, larger blocks and a longer scalar tail, and AMD's 512-bit compress is not twice the throughput of the 256-bit path. The instruction the algorithm was designed for is available and is the wrong choice on this machine.

The obvious benchmark harness flatters std::sort. Timing copy(src → buf); sort(buf) in a loop over the same source array makes every data-dependent branch perfectly predictable after warm-up, and below about n = 4096 the entire branch history fits the predictor:

A 9× error, and it decays as n grows — which produced a fake discontinuity, std::sort appearing to jump from 27 µs at n = 4096 to 512 µs at n = 8192 for twice the data. Comparing a branchless SIMD sort against a branchy comparison sort on that harness is not a fair test, and it is the same warm-predictor artifact that shows up in the scalar rows of the bitonic benchmarks.
