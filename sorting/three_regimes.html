Three Regimes
of std::sort

std::sort is not one algorithm. It is three algorithms and two size checks, stitched together so that whichever regime an array falls into, a different piece of the implementation does the work. This is what each piece is for, and — measured against a plain median-of-three quicksort with none of the three decisions — what each one actually buys you.

Isolating each decision's contribution needs a control: an implementation that does none of them. This repository's quicksort.cpp is exactly that — the same median-of-three Hoare partition std::sort uses internally, with no cutoff and no depth limit, recursing all the way to partitions of one. Benchmarked head-to-head against std::sort across the same size sweep, the gap between them is the value of decisions 1 and 2 — measured, not asserted.

That control is only meaningful if its partition code really is what std::sort runs for every node above the cutoff — not just asserted from reading both source trees, but shown. Instrumenting quicksort.cpp to record wall time by node size, for one sort of 1,048,576 random ints, answers that directly.

“Node size” is the size of one partition call; “excl. time” is that call's own partition-loop cost with every descendant call's time subtracted out — the technique is the same outermost-entry guard timing_size_breakdown.md uses for its ≤16 figure, generalized to nine nested size bands via successive differences. Only 21.9% of quicksort's own time is spent in the ≤16 partitions that std::sort replaces with a single insertion-sort pass. The other 78.1% — nodes from 17 elements up to the root call on the full 1,048,576-element array — is spent inside the identical median-of-three Hoare partition std::sort also calls, recursively, the exact same number of times. There's no room for std::sort to be doing that majority of the work any differently: it's the same function. Its entire measured advantage comes out of the remaining fifth.

regime 1 · n ≈ 16

The Leaf

Where the ≤16 cutoff fires before quicksort ever partitions.

Insertion sort shifts each new element backward past every larger element already placed — quadratic in the worst case, but with no recursion, no pivot selection, and a strictly sequential access pattern. At n = 16 that quadratic cost is 256 simple compare-and-shift steps; the constant factor is what matters, and insertion sort's is tiny.

Plain quicksort's constant factor is not. At n = 16 it still recurses roughly four levels deep, and every level pays a function-call frame, a median-of-three selection, and a Hoare partition loop before it has sorted anything. std::sort's first decision is to skip all of that: below the threshold it does nothing, and a single final insertion-sort pass — over the whole array, not per partition — cleans up every left-almost-sorted region at once.

regime 2 · n = 64 – 4,096

The Widening Middle

Where both implementations are running the identical partition — and the gap keeps growing, smoothly, with no crossover.

Above the leaf, both algorithms do the same thing: pick a median-of-three pivot, partition with two inward-walking pointers, recurse on each side. std::sort's only edge here is that it stops recursing at 16 elements instead of 1 — so this regime is a clean measurement of what that one decision is worth as recursion gets deeper. Measured honestly, quicksort never catches up: the margin runs 2.0× at n = 64 up to 2.7× at n = 4,096, rising the whole way.

The reason is call count, not cache behavior. Raw quicksort recurses to partitions of size 1 — roughly 2n total calls — while std::sort stops at 16 and cleans up with one linear insertion-sort pass over the whole array, roughly n/8 calls. That fixed per-call overhead (a stack frame, a median-of-three selection, a partition loop) recurs at every level all the way down for plain quicksort; std::sort pays it only down to the cutoff. The share of that overhead in the total shrinks for neither algorithm in a way that produces a crossover — it just keeps compounding in std::sort's favor.

regime 3 · n ≥ 8,192

The Safety Net

Where a decision built for adversarial input stays dormant on ordinary random data — and the widening gap from Regime 2 simply keeps going.

Heapsort is std::sort's second decision: if recursion ever passes depth 2·log₂n, abandon quicksort and switch to heapsort, which is slower on average but has no input that makes it quadratic. It exists to stop a hostile or already-sorted array from driving naive quicksort toward O(n²) — on the uniform random data measured here, that depth limit is essentially never reached, and heapsort never runs. It is insurance, and its cost shows up nowhere in this benchmark; its payoff only shows up on inputs this benchmark doesn't contain.

So what explains the numbers below? Nothing new — the same recursion- overhead mechanism from Regime 2, continuing. There is no discontinuity at n = 8,192 in a correctly measured run: quicksort's own ns/(n·log₂n) is nearly flat across this entire range (2.42 down to 2.33), and so is std::sort's decline (0.87 down to 0.69). If cache capacity affected the two differently, it would show up here — above the 16-element cutoff they run the identical partition code, so a cache effect would have to hit both equally. The margin keeps widening anyway, slowly, from 2.8× to 3.4×, for the same amortization reason as Regime 2: fixed overhead recurs at every level for plain quicksort and doesn't for std::sort.

Three decisions, and — because this repository's plain quicksort implements the exact same partition std::sort uses internally — a fair way to measure what they're worth. The insertion-sort cutoff is doing essentially all the work measured here: a real, monotonically widening margin from 1.8× at n = 16 to 3.4× at n = 1,048,576, driven by recursion overhead that std::sort pays once per ~16 elements and plain quicksort pays at every level down to 1. There is no separate cache-related regime and no crossover — that was an artifact of measuring with a harness this repo's own benchmarks have already warned against. The depth-limited heapsort fallback buys nothing on this data at all; its payoff only shows up on inputs — adversarial or already-sorted — that this benchmark doesn't contain.
