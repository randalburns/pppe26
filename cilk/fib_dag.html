The fib(4) spawn–join graph

Every cilk_spawn forks a branch that may run in parallel; every cilk_sync is a join that waits for both branches before it can add them. Four levels of the recursion, drawn as the DAG the scheduler sees.

long fib(int n){ if (n < 2) return n; // base case — a leaf a = cilk_spawn fib(n-1); // fork: may run in parallel b = fib(n-2); // continuation: runs in the caller cilk_sync; // join: wait for both branches return a + b; // combine — happens after the join }
spawn — parallel branch
continuation — runs in caller
return → arrives at a sync
base case — a leaf

How to read it

  • ↘A node forks into two edges. The teal cilk_spawn edge makes fib(n-1) available to any idle worker to steal; the dark edge is the continuation, which the same worker keeps running as fib(n-2).
  • ‖The two children of any node have no edge between them — that independence is the parallelism. On P workers they can execute at the same time.
  • ↗The dashed returns converge on the node's cilk_sync. That join is a barrier for just this frame: a+b cannot be computed until both branches have returned.
  • ■fib(1) and fib(0) hit the n<2 base case and return immediately — they are the leaves where the DAG stops growing.

Work vs. span

Work · T₁

9 nodes

Every call in the tree. Grows as Θ(φⁿ) — the serial running time.

Span · T∞

7 nodes

Longest fork→sync path (down the left spine and back). Grows as Θ(n).

Parallelism

≈ 1.3×

T₁ ⁄ T∞. Tiny at n=4; for large n it explodes as Θ(φⁿ⁄n).

The graph is shallow but wide — that gap is the whole point of divide-and-conquer parallelism. Span stays linear in n while work grows exponentially, so fib has enormous parallelism to hand the work-stealing scheduler. Source: cilk/fib.c.
