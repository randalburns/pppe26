Vectorization · find_first

Four Lanes at a Time

A loop that stops when it finds something has no trip count, so the compiler refuses to vectorize it. Doing it by hand is worth 2–3.8× — and costs no assumptions at all.

// returns the index of the first match, or -1
long find_first(const int64_t* data, long n, int64_t target);

01 What the scan does

The array below holds 16 values and the target sits at index 10. The scalar loop touches every element up to the match. The vector version reads four at a time, so it reaches the same answer in three steps instead of eleven — and it still stops early.

02 Inside one vector step

Vector 3 covers data[8..11]. Four 64-bit values are compared against four copies of the target in a single instruction. The result is not a boolean — it is a vector of lanes, each all-ones or all-zeros, which then has to be collapsed into something a branch can test and an index can be recovered from.

03 Why the compiler won't

Auto-vectorization is a planning problem. Before the loop runs, the compiler has to divide the work into whole vectors plus a remainder — and that division needs the number of iterations up front. A loop that exits on a condition it hasn't evaluated yet cannot supply one, so there is no plan to make.

04 What it's worth

8192 int64 values, L1-resident, on a Ryzen AI 9 HX 370 (Zen 5) with clang 18 at -O3. Median of seven pinned runs, in nanoseconds per call.

The crossover is about a dozen elements. With the match at index 0 the scalar version wins outright — it compares once and returns, while the vector version still loads and tests a whole register. Past that it is 2–3.8×, and Google Highway's portable hn::Find matches the hand-written AVX2 within noise, because it compiles to the same four instructions.

What makes this example unusual is what the fast version does not assume. It returns the same index, and the same -1, as the scalar loop for every possible input — no narrowed accumulator, no bound on n, nothing about the values or how many matches exist. The speed comes entirely from a capability gap in the vectorizer.
