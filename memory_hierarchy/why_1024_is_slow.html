Why 1024 Is Slow

Walking a 1024×1024 matrix down its columns takes 9.8 ns per element. Add one unused element to the end of every row — 8 bytes, in an 8 MB array — and the same loop over the same data takes 0.36 ns. The array got bigger and the code got 27× faster. Here is the entire reason, which is four bits of an address.

AMD Ryzen AI 9 HX 370 · Zen 5 L1d: 48 KB · 12-way · 64 sets · 64 B lines gcc 13.3 -O2 -fno-tree-vectorize

01A cache is not a pool. It is 64 numbered bins.

The intuition that gets people here is that a 48 KB cache holds “48 KB of whatever you touched most recently.” It does not. A line can only be placed in one set, and which set is decided by the line’s own address — there is no policy, no search, and no way for the hardware to put it somewhere less crowded.

This L1d has 64 sets of 12 lines each. Given an address, the hardware slices it: the low 6 bits pick the byte inside a 64-byte line, the next 6 bits pick which of the 64 sets the line belongs to, and everything above that is just a label to check you got the right line.

02What that costs you: 1.6% of the cache

  1. 1

    One row is 8192 bytes, or exactly 128 cache lines

    1024 doubles × 8 bytes = 8192, and 8192 / 64 = 128. A whole number of lines, and a power of two — both matter.

  2. 2

    Stepping down one row advances the set index by 128 … mod 64

    There are only 64 sets, so the index wraps: 128 mod 64 = 0. The set does not move at all.

  3. 3

    So all 1024 elements of the column want the same set

    That set holds 12 lines. Element 13 evicts element 1; element 14 evicts element 2. By the time the loop reaches the bottom of the column, nothing it loaded at the top survives — and the next column starts cold.

  4. 4

    You are using 12 lines of a 768-line cache

    12 × 64 = 768 bytes out of 48 KB. The other 63 sets are never touched. The cache is not too small; 98.4% of it is unreachable from this access pattern.

03Proving it is the set count, not the size

If this explanation is right, then the runtime should track how many sets the column can reach and nothing else. So pick paddings that land on chosen set counts and measure. The array is essentially the same size in every row below.

04The rule is not “avoid powers of two”

Look at the 1152 row in the table. It is not a power of two, and it is still slow — 6 ns, four reachable sets. What actually governs the damage is how many factors of two are in the row length measured in cache lines: 

row length in lines = lda × 8 / 64

1024 doubles → 128 lines = 27       → 128 mod 64 = 0   → 1 set
1152 doubles → 144 lines = 24 × 9   → 144 mod 64 = 16  → 4 sets
1032 doubles → 129 lines = odd       → 129 mod 64 = 1   → 64 sets

The clean statement: a row length that is an odd number of cache lines reaches every set. Each additional factor of two in that number halves the sets you can reach and doubles the pressure on each one.

And it happens again at every level

The same 128-line stride hits L2 and L3 too, because they index sets the same way. L2 has 1024 sets, so the column reaches 8 of them — 8 KB of a 1 MB cache. L3 has 16384 sets, so it reaches 128 — 128 KB of 16 MB. One padding change fixes all three at once, which is why the effect is so large: the column was missing every level of the hierarchy at once.

05What to do

  1. 1

    Pad the leading dimension, not the logical size

    Keep the matrix 1024×1024 to your code and allocate rows of 1025 (or 1032). Only the stride changes; indices, loop bounds and results do not. Cost is 0.1% more memory.

  2. 2

    Or stop walking columns at all

    Interchanging the loops so the contiguous index is innermost avoids the whole question and is usually faster still — row order here is 0.11 ns per element.

  3. 3

    Do not expect alignment to help

    Aligning the array’s base address changes nothing: the conflict comes from the distance between rows, not from where the array starts. Aggressive alignment of every row to a power-of-two boundary makes it strictly worse.

  4. 4

    Do not expect the compiler to fix it

    It cannot. Changing your array’s layout would change the meaning of your pointer arithmetic, and the cache geometry is not something it is compiling against. This one is yours.

Where this bites in practice

Power-of-two dimensions are exactly what people choose: image tiles, FFT lengths, texture atlases, matrix benchmarks, embedding widths. It is why tuned BLAS libraries copy submatrices into packed scratch buffers before multiplying — the copy costs less than the conflict misses it avoids.

How this was measured

Measured by set_conflict.c in this directory (raw output in spin_and_sets.txt). A 1024-row matrix traversed in column order, one write per element, three repetitions, best of three trials, pinned to cpu0. Compiled -O2 -fno-tree-vectorize, since vectorizing the loop would change what is being compared. Cache geometry — 48 KB, 12-way, 64 sets, 64-byte lines — is read from /sys/devices/system/cpu/cpu0/cache/index0/, not assumed.
