The TLB Cliff

A 12 MB array fits comfortably in this machine’s 16 MB L3. Walking it randomly still costs 31.9 ns per access — three times the L3 hit latency. The cache is not the problem. The problem is that before any cache can be consulted, the address has to be translated, and the hardware that does the translating ran out of room long before the cache did.

AMD Ryzen AI 9 HX 370 · Zen 5 L1 DTLB: 96 entries, measured 4 KB pages · 2 MB huge pages

01Every load is two lookups, not one

Your program never handles a real memory address. It handles a virtual one, and the hardware must convert it to a physical one before anything can be fetched. The conversion table lives in memory, which creates an awkward recursion: looking up where your data is requires reading memory, which requires looking up where that is.

The way out is to cache the translations. That cache is the TLB — the translation lookaside buffer — and it sits in front of everything. Hit it and translation is free. Miss it and the hardware walks a four-level tree, and each level is its own memory access.

02The number that matters is reach, not entries

The TLB is a cache, so it has a capacity — but its capacity is counted in translations, not bytes. What that buys you depends entirely on how much memory sits behind each translation. Same 96 entries, two very different amounts of reachable memory:

03Finding the edge by walking off it

That 96 is measured, not quoted. The experiment grows the number of pages touched while keeping the amount of data touched tiny: chase one 64-byte line per page, in random page order. Touching N pages needs N translations but only N×64 bytes of data, so translation runs out long before the caches do.

04The overflow, worked through

Back to the array from the top of this page: 12 MB of doubles, accessed in random order. Every cache number says this should be fast. It is not, and the arithmetic says why.

  1. 1

    It fits in cache with room to spare

    12 MB against this complex’s 16 MB L3. Nothing about the data is too big; an L3 hit here costs about 11.9 ns.

  2. 2

    But it spans 3,072 pages

    12 MB / 4 KB = 3,072 distinct translations, touched in random order so no two consecutive accesses share a page.

  3. 3

    The TLB holds 96

    32× oversubscribed. By the time an entry would be reused it was evicted long ago, so nearly every access takes a page walk on top of its cache access.

  4. 4

    Measured: 31.9 ns instead of 13.5 ns

    The same 12 MB on 2 MB pages needs only 6 translations — they never leave the TLB, and the access costs what an L3 hit should cost. 2.4×, entirely in address translation.

Why this one is so easy to misdiagnose

Every instinct says “12 MB fits in 16 MB of L3, so this is a cache hit, so it is fast.” A cache profiler will agree with you — the cache hit rate really is high. The time is going somewhere that most people never think to measure, and it does not show up as a cache miss because it is not one.

05Making the pages bigger

The fix is not to touch less memory. It is to cover the same memory with fewer translations.

  1. 1

    Ask for huge pages on the allocation

    Align to 2 MB and advise the kernel. This is the whole change — the access pattern, the data structure, and the loop stay exactly as they were.

  2. 2

    Then verify you actually got them

    MADV_HUGEPAGE is a request, not a promise: under memory fragmentation the kernel will quietly hand back 4 KB pages. Check AnonHugePages in /proc/self/smaps rather than assuming.

  3. 3

    Do not bother below 2 MB

    A huge page cannot back a region smaller than a huge page. Under that size the call is a no-op, which is exactly what the flat left half of the chart above shows.

double *a;
posix_memalign((void **)&a, 2 << 20, bytes);   /* 2 MB alignment is required */
madvise(a, bytes, MADV_HUGEPAGE);

/* then confirm -- the kernel is allowed to say no */
grep -A20 $(printf %x $a) /proc/self/smaps | grep AnonHugePages

Who already does this

Database buffer pools, JVM heaps, and HPC runtimes all request huge pages at startup, and it is one of the few tuning knobs that reliably pays. The reason is exactly the arithmetic above: their working sets are measured in gigabytes, and 4 KB pages would put a page walk in front of a large fraction of their accesses.

How this was measured

The sweep is tlb_walk.c in this directory: one 64-byte line chased per page in random page order, pinned to cpu0, best of three, with the core clock re-measured before the run. The line offset within each page is rotated so that consecutive accesses do not all land in the same L1 set — without that, the experiment measures set conflicts instead of translation. The 12 MB figures come from the main pointer-chase benchmark, cache_latency.c.

The L1 DTLB step at 96 entries is clean. The second-level TLB boundary is not, because past 1,024 pages the data footprint leaves L1 and cache cost grows alongside translation cost; the tax column is the honest reading there.
