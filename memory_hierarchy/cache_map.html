Measured floorplan

Strix Point Cache Map

Every capacity, latency and bandwidth below was measured on one laptop, not read off a datasheet. The chip is not the uniform 12-core part its spec sheet implies: it is two unequal core complexes that disagree about how much cache a thread gets and how much it costs to talk to a neighbor.

03What it costs two threads to share a line

A cache line is owned by one core at a time. When a second core writes it, the line has to travel — and how far it travels depends entirely on where the scheduler put the two threads. These are measured handoffs of one line, one way.

04Why a handoff costs more than a cache hit

Those four numbers do not line up with the latency scale, and the mismatch is worth chasing. Two threads sharing an L1 — a cache with a 0.78 ns hit time — take 18 ns to pass a line. Two complexes take 167 ns, which is slower than fetching from DRAM. Neither is an anomaly; the two benchmarks measure different quantities.

Latency times one uncontended load from a passive cache: the line is sitting there, nobody else wants it, and the only question is how far away it is. A handoff is a contended ownership transfer between two active cores, and it is mediated by software — the receiving thread has to notice the write by polling. That poll has a granularity, and on this machine the granularity dwarfs a cache hit.

PAUSE costs the same ~62–65 cycles on both core types, so its cost in nanoseconds tracks the clock — and the 1.56× ratio between those two quantum figures is exactly the 1.57× ratio between the two clocks. A spin loop without it polls in 0.19 ns — but removing PAUSE makes the whole benchmark slower, because a core hammering the line stops the writer from ever winning ownership.

18 ns between SMT siblings, when L1 hits in 0.78 ns
The line genuinely never moves — those two threads share one L1. So all 18 ns is apparatus: the waiter’s PAUSE quantum, the store draining out of the store buffer, and two threads contending for one core’s pipeline. This row is the benchmark’s noise floor, and it is what proves the other rows are mostly floor too.
30 ns inside CCX 1 against 20 ns inside CCX 0
Not a slower cache. The same PAUSE costs 20.1 ns on a 3.25 GHz Zen 5c core and 12.9 ns on a 5.09 GHz Zen 5 core, so most of the difference is the Zen 5c core being slower at waiting. Subtract the quantum and both complexes do 8–11 ns of coherence work, landing right on the measured L3 hit range of 8–11.9 ns.
167 ns across the fabric, when DRAM answers in 104 ns
DRAM is a one-way fetch of a line nobody owns: core → controller → DRAM → core. A cross-complex handoff is a round trip through a protocol — acquire ownership, cross the fabric to the directory, probe the remote complex, extract the line dirty out of another core’s L1, carry it back across the fabric. Several traversals against DRAM’s one, over a fabric that is power-managed on a laptop. That last part is also why this row, alone among the four, scatters between 67 and 171 ns.

Which number applies to your code

Locks and producer/consumer queues really do pay the polling quantum — a waiter there is doing exactly what this benchmark does, so 18–167 ns is the honest figure. False sharing does not. Those threads are not waiting on each other, only writing, so the cost per contended write is the coherence segment alone: roughly 8–14 ns inside a complex, ~150 ns across it.

05Four numbers the map cannot draw

Capacity and latency are only half of it. These came out of the same benchmark runs and each one changes how you write the loop. The second has its own page, because it is the one nobody believes until they see the address arithmetic.

77×

Prefetching, when the pattern is predictable

Sequential access at DRAM sizes costs 1.8 ns instead of 104 ns. The hardware issues the loads before you ask. Pointer chasing and hash probes get none of this.

32×

The cost of a power-of-two row length

A 1024×1024 matrix walked down its columns takes 9.8 ns per element. Add one unused element to each row and it takes 0.36 ns — a bigger array, 27× faster, because of where four bits sit in the address.

2.4×

Address translation, on 4 KB pages

A 96-entry L1 DTLB covers 384 KB. On a 12 MB working set that fits in L3, page walks cost more than the cache misses. One madvise for 2 MB pages removes it.

1.01×

What twelve cores add to DRAM bandwidth

One thread reads 38.5 GB/s; twelve threads read 38.8 GB/s. A memory-bound loop gets no speedup from more cores on this machine — not a poor one, none.

How this was measured

Six C benchmarks, single-threaded ones pinned to cpu0, on an otherwise idle machine. Latency comes from a randomized pointer chase — a fixed stride would measure the prefetcher rather than the cache. The core clock is re-measured with a dependent add chain immediately before every data point, because this part moves between 0.6 and 5.16 GHz and a clock sampled once at startup silently corrupts every cycle count. Capacities and associativity are read from /sys/devices/system/cpu/cpu*/cache/, not from a datasheet. Handoff costs come from a 200,000-exchange ping-pong of one line between pinned threads; the PAUSE and polling figures in §04 come from spin_cost.c, run on each core type.

Sources and raw .csv results are in this directory; the full write-up is cache_hierarchy.ipynb.
